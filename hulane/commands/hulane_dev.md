Act as Primary Agent Orchestrator. Request: $ARGUMENTS. Call `hulane_preflight`; then classify the intake size. A small change (single-domain — pure frontend/UI, pure backend, or docs — few expected files, no schema/API/auth/data-path change, risk low) skips the planner dispatch: write classification, risk, delivery policy, summary, and acceptance criteria inline and pass `size: "small"`; anything else dispatches read-only `hulane-planner` with `size: "standard"`. For frontend/UI or backend Go work, ground the summary and acceptance criteria in the repository's own guidelines documents (for example `docs/frontend-ui-guidelines.md`, `docs/backend-guidelines.md`). For backend Go work, also check whether the `modern-go-guidelines:use-modern-go` skill is available; when it is missing, include a one-line install recommendation in the intake report (marketplace `goland-claude-marketplace`, plugin `modern-go-guidelines`) — the flow degrades gracefully without it, and the dispatch-time check repeats the reminder. Pass the classification to `hulane_open_work_item`. That MCP tool must create the GitHub Issue before deriving REQ/BUG state and projection. Default delivery policy is delivery_required false and skip_allowed true (on-demand batched releases); use delivery_required true and skip_allowed false only when the user explicitly asks to release an image with this item. Spec layer: standard items default to spec_sync_required true — have the Planner read the touched capabilities' main specs at `openspec/specs/<capability>/spec.md`, return spec_sync_required/affected_capabilities/spec_delta_draft, and derive acceptance criteria from the delta scenarios; exempt only pure-infrastructure/pure-documentation standard items with the recorded reason; small items are always spec_sync_required false. For spec_sync_required items post the delta full text as one Issue comment (or a summary plus the repository path when too long) so Gate A reviews requirement, plan, design and delta together. Verify the returned state is waiting_approval, then apply the same-turn Gate A: by default apply `hulane_transition(approve_requirement, actor="orchestrator", evidence quoting the user's original request wording this turn, patch.approval_source="auto_intake")` in the same turn — when the request text contains explicit approval wording (for example 「直接做」/「预授权」), apply it with `actor=human:<user's GitHub login>` and `patch.approval_source="pre_authorized"`, quoting the exact approval words plus the date instead — the item reaches ready with the `approval_source` trail recorded and no stop, then continue straight into the post-`/hulane_approve` flow (fetch the default branch, `hulane_worktree_create` with explicit base, dispatch Coder). The approval package comment (including the delta full text for spec_sync_required items) must already be posted — same-turn approval never waives it. `spec_sync_required=true` is never a stop reason. Keep the STOP and wait for `/hulane_approve` only for the whitelist: (1) risk_level=high — the state machine rejects an out-of-bounds same-turn approval outright; (2) the Planner reported requirement ambiguity or unresolved scope_questions; (3) the user explicitly said to pause (「等我确认」). Do not create a branch, edit business code, invoke Coder, create PR, or merge while stopped. End with Work Item ID, Issue, Planner summary, Risk, Size, Delivery Policy, Spec Sync Policy (spec_sync_required plus the delta summary or the exemption reason), Acceptance Criteria, and `/hulane_approve <ID>` (only for the stopped whitelist path).
