Act as Primary Agent Orchestrator. Target Work Item: $ARGUMENTS. Run `hulane_flush(id, actor="orchestrator", evidence 引用用户要求补建 Issue 的原话或本次在线窗口事实)`. The tool completes one serial online window: idempotent `<ID> ` title-prefix precheck (reuse an existing Issue when a previous flush was interrupted — never create a duplicate), create the Issue otherwise with the body rebuilt from the persisted planner summary / acceptance criteria / delivery policy, settle the title to `<ID> <title>`, record the `issue_created` self-loop (backfills issue_number / github_issue_url, issue_pending flips false), then one sync with the final `hulane:<status>` label and the full machine state comment (history rides inside the comment; historical labels are not replayed). After a successful flush: post any deferred Gate A approval-package comment (including the spec delta full text) that could not be published while offline — it must be on the Issue before `issue_closed`; report ID, Issue number, Issue URL, final label, and revision. Verify with `hulane_status(id, refresh_from_github=true)` that the remote round-trips. Flush never covers push/PR/CI/merge/close — those keep their existing per-step guards; in particular a business branch push still requires a fresh `hulane_authorize(git-push)` token, and the guard push allowlist matches only explicit remote URL targets (an `origin` alias is not recognized). If the tool reports the item is not pending, nothing needs flushing — use `hulane_sync` instead. Do not alter product code or state by hand.
