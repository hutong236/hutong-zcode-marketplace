The user explicitly instructs to abandon $ARGUMENTS. Act as Primary Agent Orchestrator and use `hulane-control` MCP tools only. Call `hulane_status` with GitHub refresh when resuming across sessions or when local state is suspect. Refuse when the item already sits in a terminal state (`done` or `abandoned` — the state machine rejects both) or when the user's instruction is ambiguous; abandonment is irreversible. Apply `hulane_transition(abandon, actor=human:<identity>, evidence=<the abandonment reason, quoting the user's wording>)` — the abandon event is state-machine human-gated (an `orchestrator` actor is rejected outright) and requires no tester/reviewer/merge/image/spec-sync evidence; the item lands in the terminal `abandoned` state with `next_action: none`, reachable from any non-terminal state including `blocked` and `waiting_tag_confirm`. Then close out the GitHub side: for an item already bound to an Issue (`issue_pending` false) run exactly one state-verified close carrying the reason — `gh issue close <issue_number> --repo <owner/repo> --reason "not planned" --comment "<reason>"` (no token; the guard accepts this form only from `abandoned`, rejects it from `waiting_close`, and still enforces single-operation and the exact Issue number) — then record the `issue_closed` self-loop through `hulane_transition` (it backfills `issue_state: closed` while the status stays `abandoned`; the waiting_close spec gate does not apply because abandonment has no merged tree to validate). An `issue_pending` item has no Issue to close: skip the close, do NOT call `hulane_flush`, and report that its `issue_closed` stays rejected until a flush ever binds an Issue. Housekeeping: from the managed repository run plain `git worktree remove <worktree_path>` (never `--force`; a dirty or locked worktree stays and gets reported). Keep the branch by default so unmerged work stays salvageable — delete it only when the user explicitly asks to discard, with `git branch -D <branch>`. Never invoke the legacy state CLI, never hand-edit state, and never reuse this flow to bypass a failing build (that is `block`, not abandonment).
